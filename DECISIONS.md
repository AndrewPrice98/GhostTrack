## Dependencies

- **uvicorn[standard]** (>=0.30): the ASGI server for `fastapi`. FastAPI does not bundle one, and `[standard]` adds the usual speedups (uvloop, httptools, watchfiles) on Linux. It is a runtime dependency because the backend must be started by something. Same choice as the sibling projects.
- **httpx** (>=0.27), dev only: required by Starlette's `TestClient`. It is not used for outbound requests. Outbound HTTP to adsb.lol uses the standard library (`urllib.request`) with a timeout.
- No other third-party runtime dependency beyond fastapi, pyyaml, python-multipart and pyjwt.

## Data source: adsb.lol

Sources: the OpenAPI document at https://api.adsb.lol/api/openapi.json (the human docs at https://api.adsb.lol/docs are a JavaScript shell), https://www.adsb.lol/docs/open-data/api/, and one live request (below).

- **Base URL:** `https://api.adsb.lol`. It is the only host the backend may contact, and it is an allow-list constant, never taken from input.
- **Point/radius endpoint:** `GET /v2/point/{lat}/{lon}/{radius}`. OpenAPI types: `lat` number in [-90, 90], `lon` number in [-180, 180], `radius` **integer**, maximum 250, minimum 0. The summary says "up to 250nm", so radius is in nautical miles. An equivalent alias exists: `/v2/lat/{lat}/lon/{lon}/dist/{radius}`. GhostTrack uses `/v2/point/...` with `lat` and `lon` formatted from floats and `radius` from an int, so only numeric characters reach the URL (no SSRF).
- **Not used:** `/v2/mil` (military aircraft), because the project covers civil airspace only.
- **Live confirmation:** one request, `GET /v2/point/33.94/-118.41/25` at 2026-11-10 08:31 UTC, returned HTTP 200, `content-type: application/json`, `cache-control: no-store`, 15,635 bytes, 36 aircraft. The sample is not committed.
- **Response envelope (observed):** `{"ac": [...], "msg": "No error", "now": <epoch milliseconds>, "total": <int>, "ctime": <ms>, "ptime": <number>}`. `now` was `1794299503501`, which is milliseconds. This differs from readsb's own `aircraft.json`, where `now` is seconds, so the normaliser treats adsb.lol `now` as milliseconds. `msg`, `total`, `ctime` and `ptime` are not documented in the sources read and are informational only.
- **Rate limit / usage:** no numeric rate limit is published. The OpenAPI description says the API is free, that "in the future" a key will be required (obtainable by feeding adsb.lol), and that production users should contact the maintainer. GhostTrack's etiquette: at most one upstream request per region per 10 s per instance (the live view and the recorder both enforce a 10 s floor), a 3 s timeout, a fixed host and a descriptive `User-Agent`. The hosted demo is a small non-commercial portfolio demo. NOT CONFIRMED: whether a Vercel-fronted demo counts as "production" use; revisit before relying on it.
- **Aircraft fields.** Units and meanings are from the readsb JSON documentation (https://github.com/wiedehopf/readsb/blob/dev/README-json.md). Keys are omitted when data is unavailable.

## Reference facts

### ICAO 24-bit address allocation by state

- **Primary source:** ICAO Annex 10, Volume III (Communication Systems), Part I, Appendix to Chapter 9, "Table 9-1. Allocation of aircraft addresses to States". A reproduction of the Appendix is in an ICAO working paper (APIRG/26 WP/03 F12), https://www.icao.int/sites/default/files/ESAF/APIRG/APIRG-26/FR/WPs-FRE/APIRG26-WP03F12-App-Guidelines-for-ICAO-24-Bits-Adresses-Assignment.pdf (the table starts on its PDF page 5). It describes blocks defined by a fixed pattern of the first 4, 6, 9, 12 or 14 address bits, giving blocks of 1,048,576 / 262,144 / 32,768 / 4,096 / 1,024 addresses. The all-zero address must not be used.
- **Form:** the table gives each State's block as a bit pattern ("a dash represents a bit value equal to 0 or 1"), not as hex ranges, for roughly 190 allocations. Example: Canada `1100 00` followed by dashes (262,144 addresses); Argentina `1110 00`; Brazil `1110 01`.
- **No citable open hex table exists.** The widely used hex lists are in GPL projects (tar1090 `html/flags.js`, an `ICAO_Ranges` array; the file has no licence header but says it is based on dump1090 code, which is GPL). They cannot be copied into an MIT repository.
- **Decision:** GhostTrack carries its own table, `backend/ghosttrack/facts/icao_table9_1.py`, transcribed by hand from the working paper's page images (PDF pages 5-10, Annex pages I-9-5 to I-9-10) as the printed bit patterns, with the source cited in a header. It holds all 186 State rows and the 3 "Other allocations" (ICAO) rows. tar1090's `ICAO_Ranges` is used only as an independent cross-check (values compared; no code or data copied). Tests check that each pattern length matches its block-size column and that no blocks overlap. Spot checks against tar1090 all match: United States `A00000-AFFFFF`, Canada `C00000-C3FFFF`, Germany `3C0000-3FFFFF`, France `380000-3BFFFF`, Japan `840000-87FFFF`, Australia `7C0000-7FFFFF`, Mexico `0D0000-0D7FFF`. tar1090 shows the UK as a catch-all `400000-43FFFF` with smaller territory blocks nested inside; lookups use longest-match.
- **Consequences:** the edition reproduced is older (it names Yugoslavia, Swaziland, the former Yugoslav Republic of Macedonia; it has no Serbia, Montenegro or South Sudan). Addresses outside every block are "unknown". `899000-8993FF`, which tar1090's list (cross-check only; NOT CONFIRMED from a primary source) labels Taiwan, is in this table an ICAO block "allocated for special use in the interest of flight safety". Such addresses resolve to an ICAO block with no State, and GT-006 does not evaluate them.
- **Registration prefixes:** `backend/ghosttrack/facts/registration_prefixes.py` maps the nationality marks of 51 States (North and South America, Europe, the Middle East, Asia-Pacific) to Table 9-1 State names. Nationality marks are assigned under ICAO Annex 7 from the ITU call-sign series; the marks were cross-checked on 2026-11-10 against https://en.wikipedia.org/wiki/List_of_aircraft_registration_prefixes (facts only, our own format). Marks that list flags as "not in the ICAO document" (Thailand `U`, Russia `RF`, Spain `EM`, UAE `DU`) are left out. Unlisted prefixes are "unknown".
- **Licence of the table:** ICAO publishes Annex 10 with copyright reserved; the working paper carries no explicit licence text that was visible. The allocations are factual data, so only the minimal derived facts (address range to State name) are shipped, with attribution to Annex 10 Vol III Part I Appendix to Ch. 9. NOT CONFIRMED: any ICAO licence for redistribution; the residual risk is recorded in THIRD_PARTY.md.

### US N-number to ICAO address mapping

- **No public description of the algorithm was found.** What is public is the extent of the block, `A00001` (N1) to `ADF7C7` (N99999), and a set of registration/address pairs: the README of https://github.com/guillaumemichel/icao-nnumber_converter (GPL-3.0; PyPI `icao-nnumber-converter-us`) lists 9 pairs and calls the mapping "somewhat intuitive, but not convenient to implement", without describing it. A Java gist, https://gist.github.com/jwoschitz/9a5195b36f0cc7d25455283923df083f, is reported by a search summary to check the same range (not read). The FAA registry pages (https://registry.faa.gov/AircraftInquiry/Search/NNumberResult?nNumberTxt=...) show "Mode S Code (Base 16 / Hex)" but returned HTTP 403 to automated fetch, so they cannot be cited for pairs.
- **The algorithm in `backend/ghosttrack/icao.py` is our own derivation** from the structure of US registrations below, validated by the published and observed pairs. It is not a transcription of an official specification.
- **Licence consequence:** the converter is GPL-3.0, so its code is not copied. The project is used only for its published reference pairs (facts).
- **Structure:** N-numbers are `N` + a first digit 1-9 + up to 4 more characters. Letters exclude `I` and `O` (24 letters), at most two letters, and only after 1-3 digits; after 4 digits at most one letter; after 5 digits none. Within a prefix the order is: the number itself, then its letter suffixes in order (`A`, `AA`..`AZ`, `B`, `BA`..), then the children with next digit 0-9. Block sizes: suffix block 601, 5-digit leaf 1, 4-digit node 35 (itself + 24 letters + 10 leaves), 3-digit node 951, 2-digit node 10111, 1-digit node 101711. Nine first digits x 101,711 = 915,399 addresses, ending at `A00000 + 915399 = ADF7C7`.
- **Validation:** `backend/tests/test_icao.py` checks all 38 pairs below in both directions, edge cases that follow from the published pairs (N1ZZ is immediately before N10 = a0025a; N9999Z is 10 before N99999 = adf7c7; N1000A = N1000 + 1; N1AA, N10AA, N9ZZ, N99), rejection of invalid registrations, and that address -> N-number -> address round-trips across the block (all 915,399 addresses were checked once; the test samples every 7th).
- **Reference pairs.** Source A = the converter README (9 pairs). Source B = the adsb.lol live sample of 2026-11-10 (`r` registration with `hex`); adsb.lol registration data is not the FAA registry itself, so these are secondary evidence, but each independently agreed with the algorithm.

### ADS-B emitter categories

- **Source:** https://mode-s.org/1090mhz/content/ads-b/2-identification.html (identification message, TC/CA table; (c) 2021 Junzi Sun, no licence named on the page). It is a secondary source; the primary standard is RTCA DO-260B section 2.2.3.2.5.2 (not obtained; NOT CONFIRMED against the standard text). The mapping of type code to set letter (TC 4 to set A, TC 3 to set B, TC 2 to set C, TC 1 to set D) is not stated on that page; it is inferred and agrees with the live sample (`C1` and `C2` on ground vehicles, `A3`/`A5` on airliners).
- `A0` / `B0` / `C0` / `D0`: no category information.
- **Set A (TC 4):** `A1` Light (< 7,000 kg; < 15,500 lb); `A2` Medium 1 (7,000 to 34,000 kg; 15,500 to 75,000 lb, "Small" in US wording); `A3` Medium 2 (34,000 to 136,000 kg; 75,000 to 300,000 lb, "Large"); `A4` High vortex aircraft (the B757 is the usual example); `A5` Heavy (> 136,000 kg; >= 300,000 lb); `A6` High performance (> 5 g and > 400 kt); `A7` Rotorcraft.
- **Set B (TC 3):** `B1` Glider / sailplane; `B2` Lighter-than-air; `B3` Parachutist / skydiver; `B4` Ultralight / hang-glider / paraglider; `B5` reserved; `B6` Unmanned aerial vehicle; `B7` Space or transatmospheric vehicle.
- **Set C (TC 2):** `C1` Surface emergency vehicle; `C2` Surface service vehicle; `C3` Ground obstruction; `C4`-`C7` reserved.
- **Set D (TC 1):** reserved. readsb documents the category field as `A0`-`D7`.
- The lb thresholds for A1/A2/A3/A5 come from search-result excerpts of ADS-B Exchange and airplanes.live pages (both returned HTTP 403 when fetched directly), and agree with the kg thresholds on mode-s.org (7,000 kg is 15,432 lb; 34,000 kg is 74,957 lb; 136,000 kg is 299,824 lb, so the kg values are rounded versions of the lb ones).
- **Decision:** `C1`, `C2` and `C3` are treated as ground traffic and excluded from airborne kinematics.

## Ingest and recordings

- **Region:** `socal`, centred on LAX (33.94, -118.41), radius 60 NM, in an allow-listed `REGIONS` dict. The URL is `https://api.adsb.lol/v2/point/{lat:.4f}/{lon:.4f}/{radius:d}`; only numbers reach the path and the host is a constant.
- **Dedicated opener.** `upstream.make_opener()` builds an `OpenerDirector` with an empty `ProxyHandler({})` (environment proxies are ignored), HTTPS only (plain HTTP, file and ftp handlers are not registered), and a redirect handler that refuses every 3xx (`UpstreamError`, status kept). `fetch_raw` also checks that the URL is `https://api.adsb.lol`. The base URL can only be changed through the underscore-prefixed `_base_url` argument, which only tests pass (to a 127.0.0.1 test server); no config or environment variable reaches it.
- **Limits:** 3 s per socket operation plus an 8 s wall-clock cap on the whole body read (`read1` is used so a slow drip cannot sit inside one blocking read), and a 5 MB body cap (Content-Length precheck plus a streamed cap). Non-JSON and wrong envelopes raise `UpstreamError`.
- **Errors carry the HTTP status** (429, 5xx, refused 3xx, or "timeout"). The recorder honours `Retry-After` on 429 (seconds form only, capped at 120 s) and otherwise doubles its delay up to 60 s.
- **Military exclusion is best effort.** Because `dbFlags` is not delivered, a record is dropped if `dbFlags & 1` (when present) or its ICAO address is in the US DoD block `AE0000-AFFFFF`. Military aircraft with non-US addresses, or US military aircraft using addresses outside that block, are not caught; this is documented in the README. Both paths are unit-tested, dropped records are counted under `military`, and a test asserts that no committed recording contains a DoD-block address or a `dbFlags` bit. The same normaliser (`normalize_record`) serves live ingest, the recorder and uploads.
- **Sanitisation:** per record, an invalid `hex` (not 6 hex chars, so `~` non-ICAO addresses too), a non-object record, a missing or out-of-range lat/lon (+-90/+-180) or a duplicate ICAO drops the record. Out-of-range optional fields (`gs` 0-2000, altitudes -2000..60000, rates, `track`, `seen_pos`, `rssi`, `nic`/`nac_p`) are cleared to `None`; text fields must match strict patterns. Everything is counted in `dropped_by_reason`.
- **Units and semantics:** altitude ft, speed kt, rates ft/min (as delivered). `alt_baro: "ground"` gives `on_ground=True`, `alt_baro_ft=None`. `source` is `mlat` if `type == "mlat"` or `"lat"` is in the `mlat` list; `tisb` likewise; `adsb_icao`, `adsb_icao_nt` and `adsr_icao` give `adsb`; everything else is `other`. `adsb_other` / `adsr_other` map to `other` because they carry a non-ICAO (anonymous or self-assigned) address whose position quality differs from a regular ICAO source, so kinematic tolerances must not treat them as plain `adsb` (they are mostly dropped anyway, since such addresses start with `~`). Snapshot `ts` is `now / 1000`.
- **Stored `ts` bounds:** the envelope `now` must be 0..4e12 ms (1970..2096). This only rejects garbage; the value is still untrusted and falls back to local time when absent or invalid.
- **Recorder** (`backend/scripts/record.py`). One sequential poll per interval, 3 s timeout, a default of 10 s and a hard floor of 10 s (a smaller `--interval` is refused, so the recorder keeps the same etiquette as the live view), duplicate upstream frames skipped, `--region` restricted to the allow-list, an existing recording not overwritten without `--force`, and stale or interrupted `.tmp` files removed. Recordings are `backend/data/recordings/*.jsonl.gz` (one normalised Snapshot per line) plus `manifest.json` (name, start/end UTC, snapshots, aircraft, sha256); `record.py --check-manifest` verifies it.
- **The committed recordings:** five 20-minute windows of region `socal`, all from 2026-11-10.
  - `socal-a`, `socal-b`, `socal-c`: three contiguous windows, 08:39-09:39 UTC (00:39-01:39 Pacific, overnight, so traffic is light: 48-60 distinct aircraft per window). They were taken at a 5 s cadence, which drew about 59 HTTP errors in total (likely upstream throttling); the recorder backed off, so each file holds about 200 of a possible 240 snapshots with occasional 10-20 s gaps. That is the reason the recorder's floor is now 10 s.
  - `socal-d` 16:00:33-16:20:23 UTC (116 snapshots, 275 distinct aircraft) and `socal-e` 16:20:48-16:40:38 UTC (116 snapshots, 326 distinct aircraft), 08:00-08:41 Pacific, at a 10 s poll; 2 timeouts each (backed off 20 s). Snapshots are about 10 s apart, so a file holds 116 rather than 200 snapshots. Their reports include `tisb` as well as `adsb` positions.
  - Across all five files: 57,227 aircraft reports, none in AE0000-AFFFFF, none with a `dbFlags` bit, none injected.
- **Baseline caveat:** the recordings do not cover other days, weekends or evening peaks. Re-record with `scripts/record.py` (a new name, then `scripts/build_demo.py`) for a broader baseline.

## Tracker and detections

- **Tracker (`backend/ghosttrack/tracker.py`).** Tracks are keyed by ICAO address. Each point carries its true position time, `snapshot ts - seen_pos`; with 5-10 s polling the snapshot time alone would turn late or repeated positions into fake jumps. Positions older than 60 s are stale and never feed kinematics; a position without `seen_pos` has an unknown age and is not used for jumps. Repeated positions (same position time and coordinates as the previous point) are marked and skipped by position checks. A gap over 5 minutes (between appearances or between position times) starts a new segment; detections never compare across segments. Distances are haversine on a sphere (`geo.py`), so the antimeridian and poles need no special cases.
- **Detections (`backend/ghosttrack/detections/`).** GT-001 to GT-010 are pure functions `(track, context)` (GT-009: `(all tracks, context)`) returning an `Evaluation`: findings plus coverage (checks run and not-evaluated reasons). Status is "flagged", "clean" (something was checked) or "not_evaluated" (nothing could be checked); a detection never reports clean for inputs it did not have. Findings carry `detection_id, icao, ts_first, ts_last, severity, confidence, evidence[{field, observed, threshold, ts}], explanation, benign_causes`. Violations of one detection closer than 60 s are merged into one finding (an episode).
- **Thresholds live only in `detections/catalog.yml`** (loaded by `ghosttrack/catalog.py`), including the tracker's timing rules (`common.segment_gap_s`, `stale_position_s`, `repeat_position_time_s`, injected into the tracker as `TrackerSettings`), every confidence value and the evidence cap. Tests edit catalog values and check that behaviour changes. Each detection has a rationale, false-positive notes, benign causes and references, and there are per-emitter-category limits (A1-A7, B1-B7, unknown) with rationale. Limits are generous ceilings, not typical performance. Ground traffic (on-ground reports, C-category, including reports that lack a category on a C-category track) is excluded from airborne kinematics. MLAT/TIS-B data gets a documented 1.5x factor on kinematic thresholds, a 1 NM position allowance per point and 0.6x confidence. Points without a category use the track's most common category.
- **Persistence rules** (all in the catalog, all generic noise suppression): GT-001/002/003 need two violations in an episode; GT-002 ignores a single altitude spike that returns; GT-005 needs two out-and-back jumps faster than Mach 3 in an episode (`min_alternations: 2`; one out-and-back is a single bad decode and is GT-004 only), or two reports in the same snapshot; GT-007 needs 3 reports over 15 s; GT-008 needs an emergency code held for 2 minutes (2 reports for a surface vehicle) and is informational only. GT-009 requires every pair of cluster members to be similar, and reports each address in at most one cluster.
- **Severity and the budget.** GT-008 is always `info` (confidence 0.2); GT-003 and GT-010 are `low`. They are shown but not budgeted (see Validation and the false-positive budget).
- **GT-007 band:** 1,500 ft pressure band (QNH 958-1068 hPa; a near-surface figure, generous aloft) + 0.08 x pressure altitude (altimeter temperature error of about 4 % per 10 C, for a +-20 C mean column deviation; 0.12 was tried and judged too loose) + 350 ft geoid.
- **GT-006 is conservative:** it flags only when a valid US N-number converts to a different address, or when both the address block State (Table 9-1) and the registration's nationality-mark State are known and differ. Unknown prefixes, unallocated addresses and ICAO blocks are not evaluated. adsb.lol's `r` comes from adsb.lol's database keyed by the address, so on live data GT-006 mostly finds database or re-registration inconsistencies.
- **Behaviour on the committed recordings** (`python scripts/detect_recordings.py`): 0 findings of severity medium or high on every recording. The three overnight recordings (60, 54 and 48 tracks) produce no finding of any severity; 26-30 airborne tracks per recording are evaluated by the kinematic checks (the rest are on the ground or surface vehicles), every track is evaluated by GT-006 (all clean), and 6-7 genuinely new arrivals are evaluated by GT-009. The two daytime recordings produce only low-severity GT-010 findings (see Known limitations).
  - With every persistence rule relaxed to a single sample, exactly one raw event appears in the overnight data: N224LA (`a1f0d8`, AS50 helicopter, socal-a) reported geometric altitude -925/-975 ft against 1150 ft pressure altitude for its first two reports (5 s), with NIC 1; from the third report NIC rose to 5 and the difference returned to +50 ft. It is a real data anomaly with a known benign cause (GNSS height not yet converged, flagged by the aircraft's own low NIC), so the 3-report / 15 s persistence rule is kept and the event is not alerted.
  - Headroom: scaling all kinematic limits and the GT-007 band down, the first alerts appear at 0.6x (GT-001: widebodies at 510 kt against a 480 kt scaled A5 ceiling), so the ceilings are not tuned to the edge of the data. The largest implied speed between positions was 524 kt (B772, gs 510 kt), the largest vertical rate 4,736 fpm, the largest along-track acceleration 0.57 g (a take-off transition, excluded by rule), and the largest geometric/pressure difference outside the startup event +1,300 ft at FL310, 0.30 of its 4,330 ft tolerance. The startup event is 1.09x its tolerance (2,125 ft vs 1,942 ft) for 2 reports, below the 3-report rule.
  - No threshold has been changed to suppress an observed alert.

## Validation and the false-positive budget

- **Scenarios (`backend/ghosttrack/scenarios/`).** Seven documented, seeded attacks are injected into a recorded window (`socal-a`, from 240 s in, after GT-009's warm-up): single ghost (1,350 kt airliner), ghost flood (30 aircraft in a 6 x 5 grid, 1.5 NM apart, same speed and track), ICAO hijack (a real recorded address also reported 45 NM away on alternate polls), position offset (a real track shifted 20 NM sideways in one report and kept there for the rest of the flight; caught by GT-004 at the jump), teleport (150 NM jump), altitude spoof (geometric 8,000 ft above pressure, band 3,450 ft) and registration mismatch (N12345 on a non-matching address; a British mark on a US address). Each states what it simulates, a reference and the expected detection. References are published research only (Costin and Francillon, Black Hat USA 2012; Schäfer et al., ACNS 2013; Strohmeier et al., IEEE Commun. Surveys & Tutorials 2015; Humphreys et al., ION GNSS 2008), cited as attack background only (the Schäfer et al. abstract could not be read, so no claim beyond its title is made), not for any parameter. Scenarios are data only; nothing is transmitted.
- **Labelling.** `State.injected` (default False; serialised; old recordings lack the key and load as False; the upstream normaliser always sets False). Every state a scenario adds or alters has `injected=True`; tests compare against the recording to prove nothing else changes. Invented aircraft use addresses `ADF800`-`ADFFFF` (the unallocated tail of the US block, above N99999 = ADF7C7, below the DoD block), which a test asserts never occur in any committed recording. Hijack and offset keep a real recorded address by design.
- **Validation (`ghosttrack/validate.py`, `python -m ghosttrack validate`).** `run_validation()` returns `ValidationResult(scenario, expected, fired, passed, time_to_detect_s)` plus a collateral count of medium+ findings on untouched aircraft, which also fails the scenario in the CLI. A finding is attributed to a scenario by its address (GT-009 by its member addresses). The command prints the scenario table, the documented-gap table and the false-positive table, and exits 1 on a failed scenario or an exceeded budget. Its output is pasted verbatim into the README, and `test_readme.py` fails if the two drift.
- **Time to detect** is found by replaying prefixes of the snapshots (binary search) to the first poll at which every expected detection has fired, measured from the start of the injected behaviour (for the teleport, from the jump). It has the resolution of the poll interval: values are multiples of the snapshot spacing (about 5-6 s in `socal-a`, the recording the scenarios use; about 10 s in the daytime recordings and in live mode), and 0 means "detected on the first injected report". Current values: single ghost 15 s, flood 0 s, hijack 10 s, offset 0 s, teleport 0 s, altitude spoof 20 s, registration 0 s. Single ghost and hijack also trigger GT-004 (expected: the same positions are also impossible jumps).
- **`gradual_drift` is a documented gap** (`GAP_SCENARIOS`; not scheduled into the demo and not one of the seven): a real track dragged 0.1 NM per poll up to 20 NM (more than 10 NM within the 20-minute recording). No detection fires on it, and `validate` prints `GAP HOLDS`. A gap that starts firing is reported `GAP CLOSED` and fails validation, so the scenario must then be promoted with an expectation. A consistent slow drag-off within the kinematic limits is a known blind spot of single-receiver plausibility checks; it needs multilateration or an independent receiver.
- **The false-positive budget counts only findings of severity medium or high.** GT-003 and GT-010 (low) and GT-008 (info) are reported and shown but not budgeted. Budget = max over recordings of (counted findings / recorded hours) x 1.5, never below 1 per hour, stored as `validation.fp_budget_per_hour` in `catalog.yml`. `test_false_positive_budget` reads every recording in `manifest.json`, so recordings added later count automatically; a test asserts the catalog budget is at least what the rule gives for the measured rates, and `validate` prints a NOTE when the catalog budget is looser than the rule.
- **Measured over all five recordings (about 1.66 h):** 0 counted findings on every recording, so the maximum rate is 0 per hour and the rule leaves the budget at the **1.0 per hour floor**. One counted finding in a 20-minute recording is 3 per hour, so a single false positive on any recording fails the test until the budget is revisited. The overnight recordings produce no finding of any kind; the daytime ones produce 114 low-severity GT-010 findings and nothing else (see Known limitations).
- **The baseline is thin:** five recordings, about 1.7 h, all from one calendar day and one region; the two daytime recordings are back to back in one morning, not spread over days, evenings or weekends. The 1.0 per hour floor is a placeholder, not evidence.

## Storage, replay and live view

- **Auth** (`auth.py`, `config.py`): the `GHOSTTRACK_` prefix and cookie `ghosttrack_session`; PBKDF2-SHA256 (600k iterations), a signed JWT in an httpOnly SameSite=Strict cookie that never appears in a response body (scoped to `/api`), algorithm pinned, a per-IP login limiter, dummy-hash verification for unknown users, fail closed when unconfigured, and guests only in demo mode and never writers. The login limiter is per process and unbounded in memory; behind several instances each counts separately (documented in `auth.py`). `python -m ghosttrack create-admin` prints the variables (it writes nothing).
- **Configuration.** Every variable is read through a function so tests can override it, and a blank value counts as unset everywhere (a hosting dashboard or a copied `.env.example` line that is left empty must not turn into `Path("")` or `float("")`). Every line of `.env.example` is commented out for that reason, and a test loads the file verbatim.
- **Schema** (`db.py`, SQLite, WAL): `snapshots` (rolling 30-minute window per source and region, unique on source/region/ts), `alerts(id, fingerprint, source, detection_id, severity, icao, callsign, first_ts, last_ts, injected, confidence, explanation, benign_json, evidence_json, status, notes)`, `runs`, `meta`. Alerts older than 24 h and snapshots older than the window are pruned on every catch-up or fetch. `source` is `recorded` (demo replay), `live` or `upload`.
- **Alert identity.** Fingerprint = source, detection, address and the 5-minute bucket of the episode start. Because a sliding window can move an ongoing episode's start into another bucket, an existing alert of the same source, detection and address that touches the new interval within 120 s is extended instead of duplicated (tested over a window sliding one snapshot at a time). Fleet alerts (no address) are deduplicated across sliding windows by the same rule plus at least one shared member address. `status` and `notes` are never overwritten by re-detection. Severity medium or high starts as `new`; low and info findings are stored as `info` (shown, not triaged, not budgeted). When an alert grows from low or info into medium or high, an `info` status becomes `new`; `acknowledged` and `dismissed` are never overwritten.
- **`injected` on an alert** is 1 when any state of the finding's address(es) in the finding's time range (plus 65 s) is injected; a fleet finding uses its member addresses. Tests prove no alert in a full demo cycle is un-injected.
- **Live view** (`live.py`). One upstream request per region per interval (`GHOSTTRACK_LIVE_INTERVAL_S`, default and floor 10 s, on a monotonic clock), serialised by a lock so concurrent requests share one fetch; requests arriving while a fetch is in flight do not queue behind it (they get the cache, or the replay when there is none). A failure is cached for the same interval so an outage is not retried per request. Every success is stored in the window, the detections run over it and alerts are upserted. Responses carry `Cache-Control: s-maxage=10, stale-while-revalidate=30`. The last good snapshot is served for up to 30 s when a refresh fails; after that, or on a timeout or 429, the view is the recorded replay with `source: "recorded"`. Notices: `Showing live data from N s ago`, `Loading live data; showing recorded traffic` (a request that arrives while the first fetch is running) and `Live feed unavailable; showing recorded traffic`. The live view overlays the replay's currently injected aircraft (all `injected: true`), so a visitor always sees labelled injected traffic; upstream states are never injected.
- **The upstream clock is untrusted.** A snapshot whose time is more than 300 s from the local clock is stored and shown with the local receipt time, and pruning uses `min(snapshot time, local clock)`, so a hostile or wrong `now` can neither wipe the window nor poison it (tested with +-1e9 s and +-4000 s).
- **Demo replay** (`demo.py`). The three overnight recordings (`demo.DEMO_RECORDINGS`) are concatenated into one 3,596 s cycle (602 snapshots) that repeats on the wall clock each 3,600 s. The daytime recordings are not part of the cycle: concatenating recordings taken seven hours apart would break it, so they feed validation and the budget only. The snapshot at offset `o` is stamped `floor(now/3600)*3600 + o`, a pure function of the clock, so catch-up is idempotent across the hour boundary and restarts, and a cold start equals a stepped run (tested). The seven scenarios run in the cycle every 420 s from 300 s, in the order single ghost, flood, hijack, teleport, altitude spoof, registration mismatch and (last, because it persists to the end of the cycle) the 20 NM position step. Each is applied to the rest of the cycle starting 240 s before its injection time; every added or altered state is `injected`. The catch-up throttle is per region and starts only after a successful catch-up; after a failure the next attempts for that region are held back 5 s and the error is logged once per 60 s.
- **Precomputed alerts.** `scripts/build_demo.py` runs the tracker and detections over the whole cycle (not a rolling window) and writes `data/demo_fixture.json`: 10 alerts per cycle (GT-001, GT-004 x4, GT-005, GT-006 x2, GT-007, GT-009), every one on injected data and none on untouched traffic. Between 240 and 242 alerts (23 full cycles of 10 plus partial cycles, depending on the time of day) are loaded on a cold start covering 24 h. The cold-start seed is one `BEGIN IMMEDIATE` transaction with a re-check under the lock (rolled back wholly on failure; concurrent seeders produce exactly one seed). Live mode instead computes on the fly over the rolling window, and the cycle's seam (last snapshot to first) is never analysed, so recorded aircraft jumping there raise nothing.
- **Alerts are published at detection time with no future state.** Each fixture template carries `detected_at`, the cycle offset of the first snapshot at which a prefix replay (the same method as `validate._time_to_detect`) already raises that alert, and `initial`: severity, confidence, explanation, benign causes and evidence as that prefix replay produced them (for the ghost: "1350 kt in 2 reports", not 24). A template is published once `now >= cycle start + detected_at`. Before the episode ends the replay publishes the `initial` version with `last_ts` clipped to now and evidence no later than now; at or after the end it publishes the final version (the upsert extends `last_ts`, takes the max severity and confidence and replaces the explanation and evidence). There are two versions only, with no intermediate growth, and `first_ts` stays the event start and the fingerprint key. Re-stamping skips an alert only when an existing one for the same detection and address already covers the clipped interval. This restores the time-to-detect table for the replay (tests compare to validation within 6 s).
- **Fixture determinism and staleness.** Floats are rounded to 3 decimals, the GT-009 member list is sorted, and the digest ignores CRLF in `catalog.yml`. `.gitattributes` pins the fixtures to LF and marks `*.gz` binary. NOT CONFIRMED: byte-identical trig results across platforms; the CI `--check` on Linux is the test. `demo.inputs_digest()` hashes the catalog, the schedule and **every recording in the manifest** (not only the demo cycle's three, because the API fixture's false-positive measurement reads the daytime recordings too). It covers inputs, not code: a code change that alters the fixtures is caught by CI `build_demo.py --check` and by the suite, not by the runtime digest. A stale demo fixture makes the instance compute the templates itself; a stale API fixture makes the data routes answer 503.
- **One entry point for the API layer: `live.get_traffic(mode, region, connect=..., feed=...)`.** It opens and closes the database itself. If opening fails (`sqlite3.Error` or `OSError`: an unwritable or missing path, a locked file) or any later call fails, it serves the current snapshot straight from the in-memory cycle (`demo.cycle_snapshot_at`, a bisect on `now % 3600`) with a notice (`Storage unavailable; showing recorded traffic`, or the live-feed notice in live mode). A live fetch whose storing fails still serves the live picture, and a stale stored replay is not served. The API must call this rather than `db.connect()` itself, so serverless cold starts with an unusable database still answer. `traffic_view(conn, ...)` is the same logic on an open connection.

## REST API

All routes live under `/api`.

- **Precomputed data.** Validation results (scenarios, time to detect, gap scenario, false-positive measurement) and each scenario's replay frames are built offline by `backend/scripts/build_demo.py` into `backend/data/api_fixture.json`; CI runs `--check` and a test compares the committed file with a fresh build. The API only reads it. If the file is missing or its input digest is stale the data routes answer 503; `GHOSTTRACK_COMPUTE_FIXTURES=true` (development and tests only) computes it on the fly instead. There are no warm-up threads.
- **Seeding.** In demo mode the database is seeded on the first request that needs it (once per process and database, under a lock), not only at startup. A failure is logged once and remembered for 60 s; data routes answer `503 {"detail": "Demo data is not available yet"}` meanwhile. `/api/live` keeps serving the in-memory replay.
- **Body size.** 64 KiB for every POST/PUT/PATCH except `POST /api/recordings`, which keeps the upload cap (4 MB demo, 10 MB local, `GHOSTTRACK_MAX_UPLOAD_MB`); a gzip upload may inflate to at most four times that cap. The cap checks Content-Length and also counts streamed bytes.
- **Uploads.** Only our JSONL snapshot format is accepted (gzip is detected by content, never by file name); each aircraft goes through the upstream normaliser (military exclusion included), and an upload's `injected` flag can only add a label, never remove one. Alerts from uploaded recordings carry source `upload`, are exempt from the 24 h retention (newest 500 kept) and are labelled "Uploaded recording (unverified)", or "Injected test data (as declared by upload)" when the file claims `injected`. Uploaded data never counts as real traffic: the evidence packs for an upload carry the same label (and the banner "UPLOADED RECORDING (UNVERIFIED)" or "INJECTED TEST DATA (as declared by upload)"), claim no adsb.lol provenance, and the summary report counts uploaded alerts in their own line, separate from recorded or real traffic. The aircraft page's label follows the origin of its points and findings in the same way. The upload route is writer-only and reads the multipart body only after the writer check, so a guest is refused with 403 before the instance spools or parses anything.
- **Live mode.** `mode=live` is allowed only when `GHOSTTRACK_LIVE=true` (default: on in demo mode, off otherwise), so a self-hosted install makes no upstream requests until the operator opts in; otherwise 403. `/api/live` is the only route with the traffic `Cache-Control`; it also sends `Vary: Cookie`. Every other response is `no-store`.
- **Flagged aircraft.** `/api/live` marks an aircraft `flagged` (the red ring on the map) only when a non-dismissed finding of severity medium or higher touched it in the last ten minutes. Low and info findings stay in the aircraft's `alert_ids`, the side panel and the alert lists but never ring a real aircraft. This is a display rule only; the detectors are unchanged (see Known limitations for why).
- **API description.** `/api/openapi.json` is writer-only (the cookie is scoped to `/api`); `/docs` and `/redoc` are not served at all, because they load Swagger UI and ReDoc from a CDN that the Content-Security-Policy blocks.
- **Search.** `GET /api/alerts?q=` matches callsign or address substrings (parameterised LIKE, wildcards escaped) over all alerts, server-side. Every other filter is allow-listed or validated, and ORDER BY uses an allow-list.
- **Errors and headers.** The last-resort 500 is generic and carries the security headers. Downloaded HTML has its own sandbox CSP.

## Dashboard

- **Pages:** the live map (`/`), Alerts and alert detail, Aircraft (index of the current picture plus a hex look-up) and aircraft detail (`/aircraft/:icao`: altitude and ground-speed charts, track map, identity and registration facts, findings), Detections (catalog with rationale, thresholds, false-positive notes, benign causes, references; validation tables; the false-positive budget), Scenarios (cards) and the player (`/scenarios/:name`), Reports (downloads plus a rendered preview) and Upload (`/admin/upload`, writers only; guests see "Admin only" and no nav link).
- **No hard-coded thresholds.** The Detections page renders `thresholds`, the budget, verdicts and results exactly as the API returns them (`humanKey`/`fmtThreshold` only format), and its baseline wording is computed from the measured recordings. A short static list of detection ids and titles in `src/lib.js` feeds the alert filter only, because the catalog endpoint also computes validation, which is slow on a cold start.
- **Map projection and window:** lat 32.55-35.35, lon -120.35 to -116.45 (wider than the 60 NM query radius so SAN is on the map). Equirectangular in nautical miles from the region centre (33.94, -118.41): x = (lon - lon0) * 60 * cos(lat0), y = -(lat - lat0) * 60, so the 20/40/60 NM range rings are plain circles. `src/geo.js` applies the same formula as `backend/scripts/build_basemap.py`, and a unit test checks the two agree on the airport reference points. Airports are for orientation only (FAA reference points): LAX, SAN, BUR, LGB, SNA, ONT.
- **Map interaction:** buttons, keyboard on the focusable map (+/-, arrows, 0), wheel about the cursor (native non-passive listener) and mouse drag; the view is clamped to the window, zoom 1-12x. Touch drag is left to page scrolling (buttons zoom and pan), so a phone user is never trapped in the map. Glyphs are not keyboard targets; the aircraft list next to (>= 1024 px) or under the map is the keyboard and screen-reader route to the same aircraft, and the SVG is `aria-hidden`. The live side panel is 296 px wide and collapsible (`aria-expanded`, remembered in `localStorage`, guarded).
- **Glyphs:** an airliner silhouette rotated by the reported track (a diamond when there is no track, a square on the ground), coloured by position source (ADS-B, MLAT, TIS-B, other) with a legend. Flagged (medium or higher): red ring and label. Injected: hatched fill, dashed outline and an INJECTED tag. Glyph and label sizes stay constant in screen pixels at every zoom. An aircraft with only low or info findings shows a "Low-severity findings only" chip and its findings in the side panel, but no ring.
- **Trails:** for flagged aircraft (at most 8) and the selected one, the last 15 min of `/api/aircraft/{icao}` track points, split where reports are more than 300 s apart (as the tracker does), refetched only when the aircraft's position or altitude changed since the last fetch.
- **Refresh:** every 10 s; paused while the tab is hidden (Page Visibility) and under `prefers-reduced-motion` (then a Refresh button only); an immediate refresh when the tab returns. Live mode is opt-in per session (sessionStorage), switching replay/live clears picture, trails, selection and in-flight replies, and the browser only ever talks to GhostTrack.
- **Alert queue:** filters are server-side and kept in the URL (the URL is the source of truth); the callsign/hex search uses `GET /api/alerts?q=` over all alerts (32 characters, 250 ms debounce), 50 per page with "Load more". ICAO values in links are `encodeURIComponent`-ed.
- **Evidence wording:** `src/lib.js` maps each evidence field to a plain-language name and a comparison kind (ceiling, band, floor, steady, match), giving lines such as "1.7x the 800 kt ceiling" or "outside the +/-3,450 ft band"; unknown fields fall back to their name.
- **Charts** are hand-rolled SVG (`LineChart.jsx`, `charts.js`): nice axes, gaps over 5 minutes break the line, injected points hollow, findings shade their time window, a pointer/arrow-key read-out, a text summary and a data table. The false-positive chart is a bar SVG with the budget line. Mini-track labels are placed off the line, on the side away from the neighbouring report.
- **Player timing.** Frames come from the precomputed replay, trimmed to the frames that hold aircraft (plus 3). The expected detection fires at injection + the validated `time_to_detect_s` and carries the "(validated)" marker (the checks need more than one report); other findings fire at their first flagged report, which is not a validated time. Playback autostarts unless `prefers-reduced-motion`, which starts paused and steps one still picture every 1.5 s; Play/Pause/step/restart/scrubber/speed are native controls. The map zooms to the scenario's extent.
- **Report preview** renders the Markdown download with a small safe parser (`replay.js`): React elements only, no `innerHTML`. The HTML report is download-only because it is served as an attachment with its own CSP.
- **Uploads page.** 403, 413 and other errors are mapped to plain messages; the API's `label` is shown as given (`OriginTag`).
- **Empty database.** Alerts and Aircraft show a call to action: a button to the upload for writers, an explanation for guests. A 503 from any data route shows a "Not ready yet" state with Retry.

## Deployment

- **Vercel serverless.** `vercel.json` builds the Vite frontend and routes `/api/*` to `api/index.py`, a Python function that wraps the FastAPI app. `includeFiles` covers everything the runtime reads: the package and catalog, `backend/data/**` (manifest, recordings, both fixtures) and the basemap. FastAPI routes on the original `/api` path, and the body-limit middleware matches `/api/recordings` on that same path (a test checks it). Nothing in the repository deploys itself.
- **The database lives in `/tmp`** (`GHOSTTRACK_DB=/tmp/ghosttrack.db`, set by `api/index.py` unless the owner overrides it) and is seeded lazily per function instance, keyed per DB path, under a lock, with a 60 s failure cache. Each instance therefore has its own copy: in demo mode an admin's changes (triage, uploads) are visible to other visitors on that instance until it recycles, and the UI says so beside the admin controls. `get_traffic` falls back to the in-memory cycle when storage fails.
- **Request body limit.** Vercel Functions refuse request bodies over 4.5 MB before the app sees them, so uploads are capped at 4 MB in demo mode and whenever the `VERCEL` variable is set. `/api/health` reports the effective cap, and the upload form checks size first and explains a platform-level refusal, which may not be the app's own JSON 413.
- **Admin login** exists only if the owner sets `GHOSTTRACK_ADMIN_PASSWORD_HASH` and `GHOSTTRACK_SECRET_KEY`; otherwise everyone is a read-only guest.
- **Hosted live view.** It is on by default in the hosted demo with a per-instance throttle, not a global one. Whether a hosted demo counts as "production" use of adsb.lol is an open question (see Data source).
- **Content Security Policy** is the same on the API and the static site (`script-src 'self'`, `connect-src 'self'`, `frame-ancestors 'none'`). `style-src` allows `'unsafe-inline'`, as in the sibling projects.
- **Post-deploy checks:** an oversize upload gives 413, `/api/health` reports `max_upload_mb` = 4, and the validation and replay routes serve.

## Known limitations

- **GT-010 raises low-severity findings on busy daytime traffic.** The two daytime recordings (`socal-d`, `socal-e`; 275 and 326 aircraft) produced 114 GT-010 findings (31 on 16 aircraft, 83 on 35 aircraft; 46 distinct aircraft), and no finding of any other detection. Examination: NIC and/or NACp reports of 0 on aircraft whose position track stays smooth; 88 of 114 on category A1 (light aircraft); 30 on TIS-B-sourced reports; 98 of 114 (about 86 %) recover to a healthy value within 60 s, typically a transmitter alternating between 0 and 8 report to report. This is not interference or spoofing; it is the "navigation source / message format changes" cause already in the catalog plus an alternating-report and TIS-B cause that GT-010 lists among its benign causes. No threshold was changed. The overnight recordings show none of it, so it appears only with daytime light-aircraft traffic.
  - **Decision:** GT-010's detector logic is left as it is. GT-010 is severity `low`, so it is not budgeted, and it is shown in the alert lists with its benign causes.
  - **Display consequence:** low findings are stored with status `info`. So that these reports do not turn ordinary aircraft into red-ringed "flagged" aircraft next to a headline of 0 counted false positives, the live map and the aircraft lists flag an aircraft only for medium or higher findings (see REST API, Flagged aircraft).
  - **Candidate fixes, not implemented:** require persistence (for example NIC 0 for more than one report), and skip TIS-B-sourced integrity values. Either would remove most of this noise, but each is a change to a detector's logic and would need its own validation.
- **The false-positive baseline is thin** (see Validation and the false-positive budget): five recordings, about 1.7 hours, one region and one day.
- **Military exclusion is limited** to `dbFlags` (when present) and the US DoD block. Non-US military traffic may appear.
- **GT-008 has had no real-traffic exercise:** no emergency squawk occurred in any recording.
- **`gradual_drift` is invisible** to single-receiver plausibility checks (see Validation and the false-positive budget).
- **Upstream client leftovers, all low impact:** the total deadline covers the body read only (connect and header reads are bounded at 3 s each); an HTTP error body is not explicitly closed (the opener is per call, so nothing accumulates).
